## Part 2 — The arc of thinking

### Insight A — "Suppression is a fallback, not a feature"
**User's pivot mid-Phase-3:** the v0.5.0 dismiss feature was working code but conceptually wrong as a noise-floor solution. A great human mentor doesn't have a mute button — they self-edit, calibrate, remember what they said, notice reactions, and adjust. An advisor that needs a mute button is admitting it can't tell signal from noise. **Phase 3 ships as safety valve, not headline.**

### Insight B — The empirical audit (548 caches / 164 router cycles / 435 USD entries / $7.82 spent)
We had been planning improvements from one session's biased advisory sample. The disk-resident data told a different story:

- **Retry cost is 84% of spend** ($6.53 / $7.82). 1555 retry calls × $0.0042 each. Halving retries saves ~$40/user/month at scale.
- **Phase classifier is broken**: 73.8% of cycles get `phase: "unknown"`. Three-quarters of cycles can't classify intent.
- **Router fan-out failing 33% of the time**: 1 lens (84×), 7 lenses (55×), 2 (23×), 3 (3×). When phase is unknown, fail-open to all 7.
- **Cross-project leak quantified**: top observation topics by frequency contain `UX: App.css global nowrap`, `STRATEGY: Kill the 11-chip picker` — neither describes pair-polymath. Articos/antimetal-clone advisories were leaking via the pre-v0.4.2 shared TIP_CACHE.
- **Inv (deep-mode) firing on 59% of cycles** — designed as exception, became rule.

**This audit changed the v0.5.1 priority order**: cost cuts came BEFORE persona tuning. Retry rate is the highest-leverage move by a wide margin.

### Insight C — UX_DESIGN scope drift (user pushback)
I had claimed "UX_DESIGN isn't relevant for this codebase" because pair-polymath is a CLI plugin with no web UI. User correctly pushed back: **the CLI commands + statusline output + advisory text + help messages + CHANGELOG/README ARE the entire UX surface.** Going back through the session data with that lens corrected:

UX_DESIGN findings that landed real value:
- Empty-state silence → onboarding hint in `pp_dismiss_list`
- "Constraints: ." sentence fragment → sentinel-stripped block
- Raw ID after dismiss add → P2 deferral
- Help text `[scope=project|global]` typo trap → I9 critical fix
- `pp_dismiss_show` minified JSON → deferred
- `printf %s` missing newline breaks scripts/copy-paste

The fix isn't "drop UX_DESIGN" — it's **scope-tightening the persona**: *"You evaluate USER-FACING surfaces only — CLI text, statusline output, error messages, README, CHANGELOG, advisory text. Internal helpers and implementation details are out of scope."* One-line addition to the lens persona template. v0.5.1.1 work.

### Insight D — PRISM (the persona accuracy/alignment tradeoff)
**Paper:** "Expert Personas Improve LLM Alignment but Damage Accuracy" (arxiv 2603.18507).

Pair-polymath's personas all read the same way: *"You are a senior X who has shipped 50+ Y and watched Z fail for the same reasons. Your job is to surface ONE concrete observation."*

That construction:
- ✓ Aligns the output (sounds role-appropriate, confident, committed)
- ✗ Damages calibration (model can't hedge, can't say "I have no signal here so I'll stay silent")

Every observed false-positive this session traces to this. Product_Biz sounds like a Product VP because we asked for it; the cost is Product-VP-shaped advice even when grounded facts say "this is a 1500-LOC bash plugin with zero users."

**The fix is changing the construction**. Instead of "You are X with strong views," try: *"You are X who has just seen this codebase for 30 seconds and is calibrated. Most of the time, you'll have nothing useful to say. Say so. Only fire when the evidence makes you genuinely curious."* Output schema becomes `{claim, confidence_0_1, why-not-silent}`. The lens has to **justify firing**, not justify silence.

### Insight E — OAR (Observation→Action Rate) — the missing measurement
Before this session, every "is the system smart enough" debate was opinion-driven. The current eval-harness measures hallucination + usefulness at *generation* time. What's missing is **outcome**: did the user actually do anything about it?

**OAR proposal:** for each advisory injected over the past N days, classify the user's next 24h:
- **acted** — subsequent commit/edit touches the advisory's cited file or symbol
- **referenced** — subsequent user-prompt quotes or paraphrases the advisory  
- **pushed-back** — subsequent user-prompt explicitly disagrees
- **ignored** — nothing

`OAR = (acted + referenced) / total`. Baseline probably 5-10%. Aspirational target: 50%+. Without OAR, every prompt change is opinion. With OAR, you can A/B test prompt rewrites in production data. This is **the prerequisite for everything else**.

### Insight F — The cycle is recursive: polymath caught its own bug
v0.4.3 fix was triggered by polymath's ENGINEERING lens surfacing `BUG: PP_BUDGET_FILE set at load time will miscount across midnight (3m)` in the statusline rotation. The bug was real, the fix took <2 hours. **This is the strongest possible signal that the system is working as intended** — when lens output is grounded (Engineering lens with file:line citation), it catches real bugs at high precision.

### Insight G — Lens signal-to-noise is asymmetric
Engineering and Security catch high-precision findings (grounded in code). UX_DESIGN catches valid issues when scoped correctly. Product_Biz / Strategic_Founder / Cognitive_Flow leak SaaS-founder template — they fire regardless of project maturity. **The fix is per-lens maturity-gating**: don't fire monetization advice unless billing/customer context is visible in grounded facts.

## Part 3 — The Ralph methodology (what worked, what evolved)

The session followed a consistent pattern across releases:

```
Pass 1 — Context swarm (3 parallel Explore agents)
   ├── Roadmap / prior-art / domain dive
   ├── Existing code mapping (file:line citations)
   └── Risk / threat-model / anti-pattern analysis

Pass 2 — Spec refinement (write spec → GPT-5 steelman → iterate)
   Typical 2-3 iterations; convergence when GPT findings shift from
   critical/important to minor/cosmetic.

Pass 3 — Implementation plan (via superpowers:writing-plans skill)
   TDD-discipline bite-sized tasks with concrete code in every step.

Pass 4 — Implementation (subagent-driven via superpowers:subagent-driven-development)
   Fresh subagent per task; pre-flight verify; commit per task.

Pass 5 — 4-way parallel review (sonnet, varies by domain)
   ├── code-refactoring:code-reviewer
   ├── debugging-toolkit:debugger
   ├── 1 domain-specific agent (security-auditor, observability-engineer, etc.)
   ├── GPT-5 review-code via llm -t review-code
   └── UX-taste (impeccable interface review) — manual or general-purpose
```

**What this caught that single-agent review missed:**
- v0.4.1 C1: `PP_BUDGET_REMAINING_PCT=0` exported forever (latent router-misleading bug) — debugger + code-reviewer caught it independently
- v0.4.1 I1: WARN >= RED inversion silently kills amber zone — all 3 reviewers caught
- v0.4.2 G1: `stat -c %Lp` is BSD-only, doctor silently passed on Linux — GPT-5
- v0.4.3 P0-1: PP_BUDGET_FILE midnight bug — polymath's own ENGINEERING lens!
- v0.4.3 P0-2: `stat -f %m` Linux silent break in inject hook — debugger
- v0.5.0 Round-1 C1: latest-wins folding gap — all 4 reviewers independently
- v0.5.0 Round-2 C1: render cache thrashes every cycle under sliding TTL — debugger

**The pattern that emerged:** 2 review rounds typically converge — Round 1 catches fundamental correctness, Round 2 catches things Round 1's fixes accidentally created. By Round 3 you're at diminishing returns (only minor / cosmetic findings).

## Part 4 — The DIM (Developer Insights Module) design

This was the major architectural conversation late in the session. Three GPT review rounds + 3-pass context swarm informed it. User scope clarification mid-thread: **"everything stays local, developer insight module context is across session and machine level, project level lenses see the repo."**

### Locked scope
- **Local-only** — profile never enters LLM API
- **Machine-wide, cross-session, cross-project** — SQLite at `~/.claude/pair-polymath/insights/profile.sqlite` (mode 0600)
- **Lenses stay repo-scoped** (unchanged from v0.5.0)
- **Outputs ONLY**: (1) router calibration weights, (2) opt-in dismiss-pattern defaults. NO persona prompt amendments (privacy stop-ship from GPT-R2 — would leak user-derived state to LLM).

### Causal design (SUTVA-preserving per GPT-R3)
- Single-lens-per-cycle in eval windows; floor + surprise paused
- Design propensities logged per unit
- Project × time blocking
- HAC/Newey-West SEs for serial correlation
- Online FDR (SAFFRON/LORD) — not batch BH (handles daily peeks)
- CUPED with pre-period OAR as covariate
- Bernoulli CUSUM auto-disable (not Gaussian σ)

### Anti-runaway safeguards
- 5% lens-fire floor enforced at scheduler (not just at weight level)
- Adjustment clamp [0.5, 2.0] of baseline (never zero a lens)
- Surprise-inject (20%) is a separate channel — DIM weights don't affect it
- Auto-disable: scoped rollback (tagged-harmful only, not blanket) + 30d cooldown
- Runtime privacy interceptor at LLM API boundary + e2e payload test + CI lint
- Meta-parameter changes capped: confidence threshold ∈ [0.5, 0.9]; aggression delta ±0.05/week

### What we explicitly do NOT build (locked)
- ❌ Time-of-day / working-hours tracking
- ❌ Commit-cadence / productivity scoring
- ❌ Keystroke / cursor / focus tracking
- ❌ Expertise inference from code patterns
- ❌ Cross-user / cross-machine sync
- ❌ Burnout warnings / engagement scoring
- ❌ Third-party telemetry export
- ❌ Persona prompt amendments from DIM (privacy stop-ship)
- ❌ Any DIM-derived content in LLM API payloads

**The line:** DIM may encode "what the user has shown by explicit dismiss + measurable observation→action correlation." It may NOT encode inferred behavioral state.

## Part 7 — Decisions and reversals

### Reversed
- **"UX_DESIGN isn't relevant for this codebase"** → reversed. CLI/statusline/advisory text IS the entire UX surface. UX scope-tightening (v0.5.1.1) instead of dropping the lens.
- **"v0.5.0 is the noise-floor release"** → reframed mid-flight to "safety-valve release" after the suppression-vs-amplification insight.
- **"Persona prompt amendments from DIM"** (R0 design) → DROPPED in R1 after GPT caught that this would leak profile to LLM API. DIM outputs scheduler-only after that.
- **"Sprint Option C (Tier 0 + Tier 1 + UX bundle)"** → reversed to Option B (Tier 0 only) after GPT R4 review pointed out lens changes would confound cost-saving attribution.
- **"P/R ≥ 0.7 fidelity gate"** → upgraded to per-lens Wilson CIs on PPV/NPV after GPT-R2 base-rate concern.

### Locked
- **DIM is stand-alone, NOT architecture rewrite** (user scope clarification)
- **Developer-model scope: machine-wide cross-session cross-project; lenses stay repo-scoped**
- **Everything local; profile never enters LLM API**
- **Off-by-default with byte-identical-STDOUT invariant** (refined from "byte-identical" after GPT-R2 pointed out side effects)
- **Auto-suppress (v0.5.0) defaults OFF — `PP_DISMISS_AUTO_ENABLE=0`**

### Deferred
- Time-of-day / working-hours / commit-cadence tracking — scope creep into productivity coach
- Cross-machine sync — privacy concern + complexity
- Expertise inference from code patterns — static analysis cost + reliability
- Sentinel rendering centralization (`lib/sentinel.sh` extraction) — noted by advisory, low ROI right now
- Atomic-write helper extraction (`lib/io.sh`) — same

## Part 8 — Methodology learnings

### What worked
1. **3-pass swarm context exploration** consistently surfaced concrete file:line citations the agents could later build on.
2. **GPT-5 review iterations 2-3 rounds** consistently converged — Round 1 catches correctness, Round 2 catches what Round 1's fixes accidentally created.
3. **Steelman both sides before committing** — the DIM steelman exercise sharpened scope to the narrow form before scope creep set in.
4. **Empirical priority beats opinion** — the data audit ($7.82 spent, 84% retries) overrode my prior intuition that persona tuning was highest-leverage.
5. **Subagent-driven implementation with TDD discipline** — fresh context per task prevents the integration debt that monolithic implementation accumulates.

### What I'd do differently
1. **Capture baseline metrics BEFORE shipping changes.** v0.5.0 went out without a baseline snapshot, so "did we improve" comparisons in v0.5.1 will be inferential. Future: baseline-snapshot.json captured at install or release-tag.
2. **Pause for cost audit earlier.** I planned 4 releases before looking at the metrics.jsonl data. The 84%-of-spend-is-retries finding would have changed v0.4.x priorities.
3. **Eval foundation before optimization.** OAR (v0.5.2) should arguably have come BEFORE the dismiss feature (v0.5.0). Without OAR, we can't tell if dismiss actually reduces noise vs hides it.
4. **Less framing flexibility mid-release.** The "noise-floor → safety-valve" mid-flight reframe was the right call but cost narrative coherence. Lock framing earlier; defer scope when intent shifts.
5. **Background watchers/polling discipline.** Multiple failed polling loops (`status` zsh-readonly, network flakes, kpi-cycle.jsonl off when SLO needs data) — design with kill switches + idle states from the start.

### Tool / agent observations
- **Opus is worth the cost for multi-file integration tasks.** Cost cut by Sonnet on mechanical tasks but Opus's judgment caught real spec ambiguities (e.g. lens JSON `.extras.system_prompt_addition` path vs spec's top-level).
- **`llm -t bounce` / `-t review-code` / `-t steelman` templates from user's CLAUDE.md were heavily used.** Cheap second opinions on architectural decisions. Recommendation: codify these as standard Ralph-loop primitives.
- **The Explore agent's "very thorough" mode is genuinely thorough.** ~500-800 word reports with file:line citations.

## Part 9 — Open questions / future research

1. **Cross-machine / cross-project profile transfer.** Senior Rust dev opening a TypeScript repo — their profile says "ignores type-annotation advisories." Per Pass-1 GPT research, no published pattern for contextual expertise scoping.
2. **Distinguishing "user mastered topic" from "user disagrees with lens".** Both look like dismissal. PersonaAgent doesn't address it. Without resolution, DIM silently learns the wrong thing.
3. **Adversarial-robust single-user personalization.** All Tay-style work assumes external attackers; the single-user analogue — user systematically training the assistant wrong — is largely unstudied.
4. **When is off-profile exploration worth the interrupt cost?** Recsys bandits assume cheap impressions; an IDE advisory has high interrupt cost. No literature.
5. **Eval ground truth at scale.** OAR is self-consistent (lens fires, user ignores → label "low precision") which is itself the filter-bubble feedback loop. Need an external ground-truth signal.
