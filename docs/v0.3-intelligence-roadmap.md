# Pair Polymath — v0.3 Intelligence Roadmap

**Constraint locked (2026-05-12):** stay bash 3.2-portable. No Python rewrite. The cycle and display are already separable; we hold the bash boundary until measured data tells us otherwise.

**Goal:** Raise the quality of observations the user sees per cycle. *Not features.* The same 7 lenses producing sharper, more differentiated, less hallucinated, more actionable observations.

**Architecture:** Cycle is a background bash subshell writing per-lens cache files; display path is a 2-second bash render that reads those caches. All LLM calls go through `run_llm` → Simon Willison's `llm` CLI → OpenAI. v0.3 keeps this substrate and improves the layer above it (prompts, schemas, critique signal, memory).

**Non-goals for v0.3:**

- Python rewrite (deferred — see v0.4 reassessment gate)
- New lenses (the 7 we have aren't differentiated enough yet — fixing differentiation first)
- New subcommands beyond what v0.2 ships
- Marketplace `plugin.json` submission (after external-user feedback validates v0.3)
- Multi-provider (Anthropic / local) — deferred to v0.4

## Phase 1: Eval harness (the meta-unblocker)

**Why first:** Every intelligence improvement after this is a vibe check without measurement. We just spent two Ralph-loop rounds debating "does this prompt produce better observations" — and we still don't have a way to answer that empirically. Build the ruler before adjusting the prompts.

**Budget:** 1 week (5 work-days), 1 PR.

**Files:**

- Create: `test/eval/fixtures/session-{01..10}.tar` — 10 frozen sessions. Each contains a snapshot of `transcript_path` content + `cwd` git state + recent commits + previous observations. Drawn from real Pair Polymath dogfood sessions (anonymized: replace any author names + project names with placeholder values).
- Create: `test/eval/golden/session-{01..10}/observation-{lens-id}.txt` — held-out reference observations per lens per session. Hand-written by a human, scored for what an "ideal" observation looks like.
- Create: `test/eval/run-eval.sh` — replays each fixture through `bin/statusline.sh`, captures the rendered observations, writes them to `test/eval/runs/${timestamp}/`.
- Create: `test/eval/score.sh` — for each generated observation, runs a single LLM call (`gpt-5`, scored against the golden ref) returning one of: `useful` / `obvious` / `hallucinated` / `missed-better` + a 1-sentence reason. Aggregates per-lens to a per-run JSON report.
- Create: `test/eval/eval.bats` — bats wrapper that asserts: (a) replay runs cleanly without errors, (b) at least N/10 sessions produce parseable observations per lens, (c) the per-lens hallucination rate stays under a configurable cap.
- Modify: `bin/statusline.sh` — add `PP_EVAL_MODE` env var that bypasses statusline rendering and just emits the raw lens observations to stdout for replay capture.
- Create: `docs/eval-harness.md` — how to add a fixture, how to update goldens, how to interpret the per-lens deltas.

**Output:** A baseline `test/eval/runs/baseline.json` showing for the current v0.2.0 main: per-lens useful%, hallucination%, retry rate, average tokens-in/out. Every subsequent intelligence change measures against this baseline.

**Gate to Phase 2:** Eval harness runs reliably end-to-end (10 fixtures, 7 lenses each = 70 observations scored in ≤10 min). Baseline JSON exists.

## Phase 2: Bash-native intelligence wins

**Budget:** 2-3 weeks. 4 PRs, one per item. Each PR adds an eval delta check to CI: if useful% drops or hallucination% rises by >5pp vs baseline, the PR is blocked.

### Phase 2.1: Lens personalities in JSON (closes issue #21)

The ai-engineer R1 finding: all 7 analysts get the SAME `prompts/analyst-primary.md` template with `${lens_group}` / `${lens_focus}` / `${lens_hats}` substituted into one sentence. Differentiation is ~3-5%. The "7 lens architecture" exists in the README but not in the code.

**Files:**

- Modify: `lenses/*.json` — add `extras.system_prompt_addition` (a 200-500 token lens-specific framing) + `extras.examples` (an array of 2-3 worked observation samples).
- Modify: `lib/lens-loader.sh` — load `extras.system_prompt_addition` into `PP_LENS_SYSTEM_PROMPT_ADDITION[$idx]` array. Load `extras.examples` joined into `PP_LENS_EXAMPLES[$idx]`.
- Modify: `lib/prompt-loader.sh` — extend `PP_PROMPT_VAR_ALLOWLIST` to include `lens_system_prompt_addition` and `lens_examples`.
- Modify: `prompts/analyst-primary.md` — restructure to interpolate `${lens_system_prompt_addition}` (the meat) + `${lens_examples}` (the few-shot block), with the generic framing dropping from 95% of the prompt to ~30%.
- Modify: `bin/statusline.sh` — pass the new vars into the per-lens analyst subshell scope.
- Modify: `test/lens-loader.bats` — add tests for the new schema fields + backward-compat (old lenses without `extras` still load).
- Modify: `test/eval/eval.bats` — assert per-lens useful% rises by ≥10pp vs baseline.

**Gate:** Eval shows ≥10pp useful% rise across ≥5 of 7 lenses. If a lens regresses, the lens's `extras.system_prompt_addition` is wrong and gets reworked before merge.

### Phase 2.2: Critique deterministic citations (new — extracted from ai-engineer R1 M1)

Today the critique LLM is asked "does this observation cite a file/symbol present in the grounded blob?" by grep-matching strings in a truncated 3KB grounded slice. False-positive DROPs cost a retry budget call and erase a valid observation.

**Files:**

- Modify: `bin/statusline.sh` — after the planner + analyst stage, deterministically extract `valid_paths` (every path string seen in `git_status`, `git_recent_files`, `cwd_ls`, `recent_tools`) and `valid_symbols` (every identifier in `file_contents` matching `[A-Za-z_][A-Za-z0-9_]{2,}`). Cap each at 200 entries.
- Modify: `prompts/critique.md` — accept new placeholders `${valid_paths}` and `${valid_symbols}`. Reframe the citation check from "match against grounded blob" to "match against this explicit allowlist."
- Modify: `lib/prompt-loader.sh` — add `valid_paths`, `valid_symbols` to `PP_PROMPT_VAR_ALLOWLIST`.
- Create: `test/citation-extraction.bats` — fixture-driven tests for the path + symbol extractors.

**Gate:** Eval shows critique false-positive DROP rate falls (measured by: an observation gets DROPPED but the retry produces a near-identical observation that passes).

### Phase 2.3: Memory feedback signal (new)

Today the model sees `prev_observations` (last 25 lines). It has no notion of which observations led the user to ACT vs which were ignored. A deterministic heuristic: if the observation mentions a file path, and the user opens/edits that file within the next 10 minutes → tag `USEFUL`. Otherwise → tag `IGNORED` (after 30 min).

**Files:**

- Create: `lib/feedback-tagger.sh` — `pp_tag_observation_outcome` function. Runs as a deferred check (next cycle inspects whether prior cycle's observations triggered file activity).
- Modify: `bin/statusline.sh` — call `pp_tag_observation_outcome` at the start of each cycle to retroactively tag the prior cycle's observations. Append the tag to `HIST_FILE_SESSION` lines.
- Modify: `bin/statusline.sh` — `prev_observations` blob now includes the tag, so lenses see `[USEFUL]` / `[IGNORED]` next to past observations.
- Modify: `prompts/analyst-primary.md` — explicit instruction: "If your past observations are mostly [IGNORED], change your angle. The user is signaling these don't matter."
- Create: `test/feedback-tagger.bats` — fixture-driven tests.

**Gate:** Eval shows `obvious%` drops (the lens learns to stop repeating itself) and `useful%` rises in long sessions (≥3 cycles).

### Phase 2.4: Reserve 9 not 23 with delta-increments (closes issue #22)

Currently `budget_reserve 23` upfront → ~60% of daily cap forfeited per cycle. The reserve-9 + delta-on-retry pattern doubles useful cycles/day.

**Files:**

- Modify: `lib/budget.sh` — add `budget_reserve_delta N` function (atomic increment within an already-reserved cycle, fails if total exceeds cap).
- Modify: `bin/statusline.sh:560` — change `budget_reserve 23` to `budget_reserve 9` (base case: planner + 7 analysts + critique). Add `budget_reserve_delta 1` at each retry entry (`:884`) and each escalation entry (`:746`).
- Modify: `test/budget.bats` — add tests for delta-increment atomicity + cap-overrun rejection.
- Modify: `docs/cost-model.md` — document the new reservation pattern.

**Gate:** Eval throughput (cycles/day before cap) doubles. No correctness regression.

## Phase 3: Reassess + ship v0.3

**Budget:** 1 week.

**Activities:**

1. Run the eval harness on the post-Phase-2 main. Compare against Phase-1 baseline.
2. If per-lens useful% has risen by ≥20pp on average AND hallucination% has fallen AND throughput has doubled → ship v0.3.
3. If any of those metrics regresses → investigate before tagging. The eval harness exists precisely to gate this decision.
4. README + CHANGELOG updates (same pattern as v0.2.0 ship sprint).
5. `VERSION` → `0.3.0`, tag, GitHub release.

**v0.3 release notes will include:**

- Eval harness + baseline JSON
- 4 intelligence improvements with measured deltas
- The decision NOT to migrate to Python, with a one-paragraph rationale

## Phase 4 (post-v0.3): The Python reassessment gate

After v0.3 ships, run the eval harness one more time and answer: **is the bottleneck for further intelligence gains the bash substrate, or is it prompts/models/critique signal?**

If the bottleneck is "model returns malformed JSON and gets silently dropped" → that's the Python sidecar moment for #24 (strict JSON Schema via Responses API). The sidecar would run only for the cycle (not display), invoked by bash, communicating via the existing cache-file IPC. Optional dependency: if Python isn't installed, the bash path keeps working with current `llm` CLI behavior.

If the bottleneck is "lenses still agree too often" or "observations are obvious" → that's another round of prompt engineering, not a substrate migration.

**Decision criteria for Python sidecar in v0.4:**

- Eval shows ≥20% of retries are caused by schema-fail (regex validation failure) → Python sidecar
- Eval shows ≥20% of cycles include a silently dropped LLM call (rc=0 but empty output, or stale cache returned) → Python sidecar
- Otherwise → another prompt-engineering round in bash

## Why this plan doesn't drift into "add features"

Every item is a sharpness improvement on an existing capability:

- Phase 1: a measurement tool for the existing behavior, not new behavior
- Phase 2.1: same 7 lenses, sharper personalities
- Phase 2.2: same critique, deterministic input, fewer false-positive drops
- Phase 2.3: same observation history, plus a usefulness signal so the lens learns
- Phase 2.4: same daily call cap, more useful cycles per day

No new lenses. No new subcommands. No new model providers. No new UI surface. The user sees the SAME tool, just smarter.

## Open questions (for the user)

1. **Eval golden references** — should they be hand-written, or generated by `gpt-5` against a reference rubric and then human-validated? Hand-written is purer; LLM-generated is 10x faster and probably good enough for relative-delta measurement.
2. **Fixture sourcing** — record 10 real Pair Polymath sessions (anonymized) or synthesize 10 sessions designed to exercise specific lenses (FINOPS, SECURITY, etc.)? Real-session fixtures are more representative; synthetic fixtures give better per-lens coverage.
3. **Phase 2 ordering** — current order is 2.1 → 2.2 → 2.3 → 2.4. Alternative: 2.4 (budget) first since it's the smallest win and unblocks longer eval runs. Trade-off: 2.4 has zero direct intelligence impact and could distract.
4. **Phase 4 gate** — is "20% of retries are schema-fail" the right Python-sidecar trigger? Could be too lax (single-digit % could already warrant Python if those failures are on high-value cycles).

Default for auto-mode if unanswered: 1: LLM-generated then human-spot-checked. 2: real-session anonymized. 3: current order. 4: ratify the 20% threshold; revisit at Phase 4.
