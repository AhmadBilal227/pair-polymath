# v0.4 Phase 3 + v0.5 Roadmap

**Status (2026-05-13):** Phase 1 + Phase 2 + Phase 2.5 shipped. v0.4 release pending (Task #34).

This doc plans the three concrete features identified after Phase 2.5 hardening landed:

1. **Phase 3 — `polymath dismiss` + memory-as-constraint** (closes noise loop, seeds audit trail)
2. **Phase 3 — `polymath history` CLI** (unified queryable audit trail, ships with Phase 3)
3. **v0.5 — `/polymath review <file>`** (on-demand observation cycle, killer interactive feature)

All three are bash 3.2-portable extensions to the existing intelligence layer. No new architectures; each builds on existing modules.

## Phase 3 — Dismiss + Memory-as-Constraint

### Goal (one sentence)

When a user marks an advisory as "intentional / already-addressed / wrong-context", that decision is persisted, fed back into every subsequent analyst prompt as a project-level constraint, and the same observation stops firing — closing the noise floor that's been the #1 user-frustration pattern across this session ("This advisory will keep firing because the lens agents don't have the architectural context").

### Architecture

Three modules, one prompt template change, two CLI subcommands.

| Module | Responsibility |
|---|---|
| `lib/dismiss.sh` (new) | Storage + query for suppression rules. Rules are id-keyed per project (project hash from `lib/memory/schema.sh:pp_memory_get_salt`). |
| `lib/memory/store.sh` (modify) | When `PP_MEMORY_ENABLE=1`, dismiss rules also persist to the memory DB so they survive `~/.claude/cache` purges. |
| `prompts/analyst-primary.md` (modify) | New `${project_constraints}` placeholder near top of system prompt. Each lens system prompt gains the stanza: *"Constraints from prior dismissals: ${project_constraints}. Do not flag these unless the diff materially changes the underlying state."* |
| `lib/prompt-loader.sh` (modify) | Add `project_constraints` to `PP_PROMPT_VAR_ALLOWLIST`. |
| `bin/polymath` (modify) | New subcommands: `dismiss`, `dismiss list`, `dismiss undo`, `dismiss show`. |
| `bin/statusline.sh` (modify) | Render `$project_constraints` once per cycle (LLM-summarized into a single canonical-form bullet block, capped at `PP_DISMISS_RENDERED_MAX_BYTES=2048`). |

### `lib/dismiss.sh` contract

```bash
# pp_dismiss_add <reason_text> [scope=project|global] [lens_id?]
#   Generates a rule via an LLM summarization call (gpt-5-mini), stores
#   to ~/.claude/pair-polymath/dismiss/<project_hash>.jsonl as one line:
#   {id, ts, reason_summary, scope, lens_id?, hash}
#
# pp_dismiss_list [scope]
#   Print all active rules (or just project, or just global).
#
# pp_dismiss_undo <id>
#   Soft-delete (set deleted=true; keep for audit). Reactivate only via
#   `dismiss restore <id>`.
#
# pp_dismiss_render
#   Build the constraint block injected into analyst prompts. LLM-
#   summarizes active rules into a single bullet list capped at 2KB.
#   Cached at ~/.claude/cache/cc-dismiss-rendered-<project_hash>.txt
#   with 24h TTL — re-renders only when dismiss file mtime is newer.
#
# pp_dismiss_auto_suppress
#   Background heuristic: if same observation hash fires >= 5 times
#   across sessions without user mentioning it in prompts, auto-add a
#   7-day-TTL rule. Runs from SessionEnd hook.
```

### Storage schema

`~/.claude/pair-polymath/dismiss/<project_hash>.jsonl` — one line per rule, append-only:

```json
{"id":"d-2026-05-13-001","ts":"2026-05-13T18:00:00Z","reason_summary":"browser-side API keys are intentional — privacy-first BYO-key design","scope":"project","lens_id":null,"hash":"sha1:abc...","deleted":false,"ttl_days":null}
```

Active rules: `deleted=false AND (ttl_days IS NULL OR ts + ttl_days > now)`.

### Tasks (TDD-discipline, bite-sized)

1. **lib/dismiss.sh skeleton + `pp_dismiss_add` + `pp_dismiss_list`** (~150 LOC, 8 fail-first bats tests). Manual rule add, list, persistence. No LLM yet.
2. **LLM summarization of `reason_text` into `reason_summary`** (~50 LOC, 3 bats tests). gpt-5-mini call, ~$0.001 per add.
3. **`pp_dismiss_render` + 24h cache** (~80 LOC, 4 bats tests). Cached LLM-summary of all active rules into the 2KB block.
4. **Wire `${project_constraints}` into `prompts/analyst-primary.md` + allowlist** (~30 LOC, 2 bats tests). Lock the contract.
5. **`polymath dismiss` CLI subcommand** (~60 LOC, 4 bats tests). Argument parsing, scope validation, help text.
6. **`polymath dismiss list / show / undo / restore`** (~80 LOC, 6 bats tests).
7. **Memory integration** (~120 LOC, 5 bats tests). When `PP_MEMORY_ENABLE=1`, dismiss rules also persist to SQLite memory DB; auto-restore on cache purge.
8. **Auto-suppress heuristic via SessionEnd hook** (~100 LOC, 3 bats tests). 5× silent fires → 7-day rule.
9. **Doctor check #16: dismiss libs + render path** (~50 LOC, 2 bats tests).
10. **Round 1 GPT plan review** → fixes → 4-way ralph review → critical-fix commit → PR.

**Total estimate**: ~720 LOC, 35+ bats tests, ~4-5 working days at the established pace.

### Gates to merge

- 368 + ~35 = ~403 bats green
- `shellcheck -S warning` clean
- Manual e2e: add a dismiss rule, verify analyst observations stop including that topic on the next cycle
- Eval-gate: useful% does not regress (the constraint stanza is informative, not censoring; net should be flat or +5pp on lenses where the constraint addresses prior false-positives)
- Doctor 16/16 green

## Phase 3 — `polymath history` CLI

### Goal (one sentence)

One queryable surface that joins the currently-scattered logs (lens caches, router-metrics, memory observations, dismiss rules, metrics.jsonl, last-cycle-payload) into a unified per-cycle audit trail.

### Architecture

| Module | Responsibility |
|---|---|
| `lib/history.sh` (new) | `pp_history_query` joins data sources into a unified record stream. |
| `bin/polymath` (modify) | New subcommand: `history` with filters. |

### `polymath history` CLI surface

```
$ polymath history --since 24h
2026-05-13 18:03 [router]   debugging      picked: ENGINEERING, SECURITY    1.7s
2026-05-13 18:03 [obs]      ENGINEERING    "Stale lens caches make line 2 blank"
2026-05-13 18:03 [obs]      SECURITY       "Tool-summary may leak secrets"
2026-05-13 18:08 [dismiss]  user           "browser-side API keys are intentional"
2026-05-13 18:12 [router]   drafting       picked: ENGINEERING              0.9s
2026-05-13 18:12 [obs]      ENGINEERING    "Untested race in run-eval cleanup"
2026-05-13 18:12 [fixed]    inferred       observation 18:03 ENGINEERING acted on (file edit matched cite)

$ polymath history --lens ENGINEERING --since 7d
[42 observations, 31 distinct, 11 acted on, dismiss-rate 7%]
...

$ polymath history --advisory-effectiveness --since 30d
Per-lens action rate (observation cited in subsequent user message within 1h):
  ENGINEERING       38% (47 / 124)
  SECURITY          22% (11 / 51)
  ...

$ polymath history --json --since 1h | jq .
```

### Tasks

1. **`pp_history_query` skeleton** (~120 LOC, 5 bats tests). Reads + merges the 5 data sources. Output is a stream of typed records.
2. **CLI argument parsing — `--since`, `--lens`, `--type`, `--json`** (~80 LOC, 5 bats tests).
3. **`--advisory-effectiveness` heuristic** (~150 LOC, 4 bats tests). Joins observation cite paths against subsequent user-message text; matches within 1h = "acted on". The proxy is imperfect but directionally useful.
4. **`polymath history` CLI subcommand wiring** (~40 LOC, 3 bats tests).
5. **Doctor: history check** (~30 LOC, 1 bats test).
6. **Round 1 GPT plan review → 4-way ralph → PR.**

**Total estimate**: ~420 LOC, 18+ bats tests, ~2-3 working days. Ships in the same release as `dismiss` (the audit trail is much more valuable with the dismiss feedback loop already in place).

## v0.5 — `/polymath review <file>`

### Goal (one sentence)

Slash-command-triggered, on-demand polymath cycle scoped to a specific file/directory/diff — turning polymath from a passive observer into an interactive consultant the user can summon for a specific question.

### Architecture

Two paths possible:

#### Path A — Standalone bash CLI (`polymath review <file>`)

User types `/polymath review src/auth.ts` in Claude Code → Claude executes `polymath review src/auth.ts` as a Bash tool call → result printed in the conversation.

| Module | Responsibility |
|---|---|
| `bin/polymath` (modify) | New subcommand: `review <file_or_dir>`. Runs a synchronous one-off cycle scoped to the target. |
| `lib/review.sh` (new) | `pp_review_run` — wraps the cycle logic from `bin/statusline.sh` into a callable function. Returns N observations + critique verdicts. |

Pros: zero new infrastructure. Slash-command is `/sh polymath review …` or a script-based slash command. Works today.

Cons: blocks until the cycle completes (~10–30s). User waits.

#### Path B — MCP server (`polymath__review_diff` tool)

Polymath runs as an MCP server. Claude calls `polymath__review_diff(file=src/auth.ts, depth=deep)` as a tool. Server returns observations.

| Module | Responsibility |
|---|---|
| `bin/polymath-mcp` (new) | MCP server stdio interface. |
| `lib/mcp/handlers.sh` (new) | Tool implementations: `review_diff`, `pre_mortem`, `check_security`, `historian`. |

Pros: native Claude integration. Tool-call UI shows in conversation. Multiple tools surface different lens "modes".

Cons: requires MCP server implementation. Architectural shift. Multi-week effort.

### Recommended for v0.5: **Path A first, Path B in v1.0.**

Path A is shippable in days, validates the demand, and Path B is the architectural upgrade once Path A proves the use case.

### Path A tasks

1. **`lib/review.sh` — `pp_review_run <target>`** (~200 LOC, 6 bats tests). Refactored cycle logic, callable.
2. **`polymath review <target>` CLI subcommand** (~80 LOC, 4 bats tests). Argument parsing (`--depth=shallow|deep`, `--lens=ENGINEERING,SECURITY`, `--json`).
3. **Scoped grounding — `pp_review_grounded_for_target`** (~150 LOC, 5 bats tests). Builds the grounded blob from `<target>` instead of the planner-picked file. Supports files, directories, git diffs.
4. **Output formatting — colored text default, JSON optional** (~60 LOC, 3 bats tests).
5. **Cost budget — `--budget=$0.05` flag, hard-cap protection** (~40 LOC, 2 bats tests).
6. **Doctor + smoke + ralph review.**

**Total estimate**: ~600 LOC, 20+ bats tests, ~3 working days. Ships as v0.5.0.

## Cross-cutting concerns

### Audit trail observability requirements (for all three features)

All three features must contribute to the audit trail per the user's question. Specifically:

- **Phase 3 dismiss**: every `dismiss add/undo/restore` writes a JSONL line to `~/.claude/cache/dismiss-audit.jsonl`.
- **Phase 3 history**: this IS the audit trail surface.
- **v0.5 review**: every `polymath review <target>` writes one router-metrics line + N observation cache writes, queryable via `history --type=review`.

### "Polymath self-review" — the meta-feature these enable

Once `history` exists, polymath can call its own history during normal cycles:

```bash
pp_dismiss_pattern_from_history    # auto-create dismiss rules from 5×-fired-then-ignored observations
pp_advisory_self_test               # run polymath against its own codebase; emit a self-report
```

These are not in v0.4 / v0.5 scope but worth flagging as where Phase 3's investment pays off later.
