## Q1 — Project-scope identity contract: **resolved**

**Decision:** Reuse `pp_memory_project_hash` from `lib/memory/schema.sh:55-73`. Same per-machine salt (`pp_memory_get_salt` at `lib/memory/schema.sh:30`), same project-hash derivation.

**Why:** Phase 3's storage path is `~/.claude/pair-polymath/dismiss/<project_hash>.jsonl`. Using the same hash as the memory subsystem means a project's dismiss rules and its memory observations share an identity — so when a user runs `polymath dismiss …` and `polymath memory …` they're talking about the same logical project.

**Caveat:** `lib/memory/schema.sh:pp_memory_project_hash` requires the memory module to be sourced. `lib/dismiss.sh` will lazy-source `lib/memory/schema.sh` rather than copy the function. This avoids two-source-of-truth drift.

**Falsifiable:** If `pp_memory_get_salt` returns an empty string (machine without prior memory init), `pp_memory_project_hash` returns `1`. `pp_dismiss_add` must fail loudly in that case (not silently write to `~/.claude/pair-polymath/dismiss/.jsonl`) — bats coverage required.

## Q2 — Observation-identity hashing for `pp_dismiss_auto_suppress`: **resolved (iterated)**

**Decision:** Use the SHA1 hash already computed at `hooks/inject-monitor-insight.sh:54`. The hash is over the full `TOPIC|||BODY` line.

**Trade-off acknowledged (from steelman):** This is exact-text matching. If the LLM rephrases the same concern with different wording, auto-suppress won't fire. A structural/semantic key (lens + normalized symbol mentions + token stems) would cluster paraphrases. **Deferred to v0.6** — adding semantic clustering is a separate research task (what tokens? what stemmer? bash-portable?) that doesn't belong in this PR.

**Counting (iterated — dropped noun-mention veto):** Auto-suppress fires when the SAME hash appears across at least **`PP_DISMISS_AUTO_THRESHOLD=10` separate sessions within `PP_DISMISS_AUTO_WINDOW_DAYS=30` days**. Both knobs configurable via env. No transcript-content checks (steelman: the noun-mention veto is sign-agnostic — a user saying *"I don't care about X anymore"* would block the auto-suppress when intent is the opposite).

**Acknowledgment channel (new):** `polymath dismiss ack <hash-prefix>` explicitly tells the system "this observation is useful, keep firing, do NOT auto-suppress". Persists in the same JSONL with `source=ack`. Acked hashes are excluded from auto-suppress count.

**Falsifiable:** Three bats tests required:
1. Same hash 10× across 10 fake session files → rule added with `ttl_days=7` and `source=auto_suppress`
2. Same hash 10× but with a prior `polymath dismiss ack` → rule NOT added
3. Same hash 9× → no rule

## Q3 — `pp_dismiss_render()`: **resolved (iterated — deterministic, no LLM)**

**Decision:** Deterministic compaction, NO LLM call. Steelman correctly flagged: predictable output + zero per-cycle cost + auditably reversible beats LLM summarization for this surface.

**Algorithm (~30 LOC bash):**
1. Read all active rules from JSONL (`deleted=false AND not-ttl-expired`)
2. Sort by `(source DESC, ts DESC)` — manual rules outrank auto-suppress; newer outranks older
3. Dedup by exact `reason_summary` match (case-insensitive)
4. Take top 8 rules
5. Format each as `- ${reason_summary}` (truncate to 200 chars per bullet, never mid-word)
6. Concatenate with `\n`; cap total output at `PP_DISMISS_RENDERED_MAX_BYTES=2048` bytes; truncate at last full bullet

**Cache:** Render-on-write only. Cached at `~/.claude/cache/cc-dismiss-rendered-<project_hash>.txt` (mode 600 per v0.4.2 umask). Re-render trigger: JSONL mtime > cache mtime, OR cache absent. No TTL needed — the cache invalidates exactly when the source changes.

**Cost:** Zero per cycle (was $0.001/cycle in LLM-render draft). No prompt template needed.

**Trade-off acknowledged:** LLM summarization could produce more cohesive bullets (e.g. merge two rules with overlapping intent). Deterministic compaction won't. **Acceptable for v0.5** — the analyst LLM downstream can do that interpretation work. If the dedup turns out to be too crude in practice (lots of near-duplicate rules), add Jaccard-on-3-grams in v0.5.1.

## Q4 — TTL semantics for auto-suppress rules: **resolved (iterated)**

**Decision:** Sliding-on-fire with a hard cap. Each match of the suppressed hash extends the rule's expiry by `PP_DISMISS_TTL_EXTEND_DAYS=3` days, up to an absolute cap of `PP_DISMISS_TTL_CAP_DAYS=30` from creation.

**Why this changed:** Steelman correctly argued that persistently-valid constraints shouldn't expire on a fixed clock — that creates re-spam exactly when the suppression is still useful. Sliding-on-fire keeps the constraint alive while it's catching things; the 30d cap prevents indefinite immortality.

**Manual rules (`source=manual`):** No TTL by default. `ttl_days=null`. Live forever unless explicitly disabled.

**Auto-suppress rules (`source=auto_suppress`):** Born with `ttl_days=7`. Each subsequent match of the suppressed hash extends `ttl_days = min(30, ttl_days + 3)`.

**On expiry:** rule moves from `active=true` to `deleted=true,deleted_reason=ttl_expired`. The observation will fire on the next cycle. Discoverable via `polymath dismiss list --ttl-expired`.

**Manual promotion at cap:** When an auto-suppress rule hits the 30d cap AND fires again, it's a strong signal the suppression is still valid. The cap behavior: rule promotes to `source=auto_suppress_persisted` with no further TTL extensions but also no expiry. Effectively "your auto-suppress was right; this is now permanent until you `disable` it".

**Falsifiable:** Three bats tests. (1) Mock clock + fire 3 days post-creation → ttl extends to 10. (2) Promote-at-cap test. (3) Manual rule never expires.

## Q5 — Memory integration: dual-write or single-source: **resolved**

**Decision:** JSONL at `~/.claude/pair-polymath/dismiss/<project_hash>.jsonl` is the canonical source. SQLite mirror is a **read-cache** only.

**Why:** Append-only JSONL is the simplest crash-safe format — no corruption risk, easily auditable with `cat`. Trying to sync writes to two systems creates a partial-failure surface (write JSONL, write SQLite, what if one fails?).

**Sync direction:** `pp_dismiss_load_into_memory()` — called from `pp_memory_maintenance` (the 1-cycle/hour SQLite maintenance pass at `lib/memory/store.sh`). Reads all-active-rules JSONL → upserts into a new `memory_dismiss_rules` table. Idempotent — same id always overwrites same row.

**Disaster recovery:** If SQLite is corrupted or `~/.claude/cache` purged, the next `pp_memory_maintenance` run rebuilds the table from JSONL. Conversely, if JSONL is accidentally deleted, the SQLite mirror is read-only and degrades to "rules invisible to render, but injected analyst prompts still warn about previously-active rules from a few cycles ago" — only until the 24h render cache expires.

**Falsifiable:** One bats test: delete the JSONL → run `pp_memory_maintenance` → verify the dismiss_rules table is empty (mirror not stale).

## Q6 — Disable / enable model: **resolved (iterated — unified commands)**

**Decision:** Unified `enable` / `disable` commands. The `deleted_reason` metadata field discriminates why.

- `polymath dismiss disable <id>` — sets `deleted=true`. `deleted_reason="user_disabled"` (vs `"ttl_expired"` set by auto-expiry, or `"ack_override"` set when `dismiss ack` overrides a prior dismissal).
- `polymath dismiss enable <id>` — sets `deleted=false`. Works regardless of why the rule was disabled. The previous `deleted_reason` is preserved in audit log.
- `polymath dismiss list` — active only by default. Flags: `--all`, `--disabled`, `--ttl-expired`, `--auto-suppress-only`.

**Why this changed:** Steelman correctly argued that `undo`/`restore` create two mental models for the same operation. Unified enable/disable + reason metadata is simpler. The footgun-prevention I designed (preventing accidental `undo` of an auto-suppress) is achieved by `disable` requiring confirmation (`polymath dismiss disable d-... --yes`) for auto-suppress rules.

**Falsifiable:** Three bats tests covering disable, enable-after-disable, enable-after-ttl-expiry.

---

## Q7 — Constraint injection placement: **resolved (iterated — placement moved)**

**Decision:** System prompt only (kept), but **placement moved from top to AFTER the lens persona declaration**.

**Why this changed:** Steelman flagged that top placement overshadows the lens persona. Placing constraints AFTER the `${lens_system_prompt_addition}` (which establishes "you are the ENGINEERING lens, your job is …") lets the persona anchor first, then the project-specific constraints inform that persona's perspective.

**Rejected alternative:** Steelman also proposed user-message-footer placement with `override d-... for this turn` syntax. **Not adopted** because: (a) constraints describe project-immutable context the user has affirmed, (b) per-turn override is overkill for v0.5 (manual `polymath dismiss disable` is the deliberate way to override), (c) user-message-footer consumes per-turn token budget. **Possible v0.6 enhancement** if dogfood reveals constraint-override-mid-conversation is a frequent ask.

**Stanza wording:** Locked. From `docs/v0.4-phase-3-and-v0.5-roadmap.md`: *"Constraints from prior dismissals: ${project_constraints}. Do not flag these unless the diff materially changes the underlying state."*

**Placement diff** in `prompts/analyst-primary.md`:

```
${lens_system_prompt_addition}

# v0.5 INSERTION POINT — after lens persona, before relevance directive
Constraints from prior dismissals: ${project_constraints}.
Do not flag these unless the diff materially changes the underlying state.

# existing
${lens_examples}
${lens_silent_example}
RELEVANCE MODE: ${relevance_directive}
```

**Falsifiable:** Bats test rendering an analyst prompt with active rules → verify the stanza appears AFTER the lens persona declaration but BEFORE the relevance directive.

## Gate criteria (refined)

Inherits canonical gates, adds:

- `pp_dismiss_render` with 0 active rules produces empty string (analyst prompt unchanged)
- `pp_dismiss_render` with 12 rules produces ≤2048 bytes ending on a full bullet
- A dismissed observation's hash NEVER appears in the injected advisory block (regression test required)
- `polymath dismiss list` of a project with 0 rules prints "no active dismiss rules" (not empty silence — bash-readable empty list)
- Eval-harness `useful%` does not regress on a synthetic project with 3 manually-dismissed observations

## Open meta-questions (for Pass-2 GPT review)

These are the design-level questions I want a steelman / opposing view on before the Pass-3 plan locks in:

1. Is the 5-fires-in-14-days threshold for auto-suppress too aggressive or too conservative? Alternatives: 3 fires / 7 days (more aggressive), 10 fires / 30 days (more conservative).
2. Is calendar-absolute TTL strictly better than reset-on-fire? Defensible counterargument: a constraint that keeps catching genuine issues should perhaps be EXTENDED, not expired.
3. Is the noun-mention veto correct? A user could mention the noun NEGATIVELY ("I don't care about X anymore") and the veto would block the auto-suppress — but that's the opposite of intent.
4. Is the JSONL-canonical / SQLite-mirror split worth the complexity vs. SQLite-canonical with JSONL audit log?
