## The pivot that drove this spec

The original v0.5.3 vision committed to a 14-subcommand `polymath agents *` workforce management surface, three subsystems (Flow Health / Friction Signal / Assistance Calibration), and an 8-state agent lifecycle. The vision included a binding prerequisite gate: **Wilson 95% CI lower bound on `acted%` ≥5% on ≥3 lenses over ≥1 week. If gate fails, v0.5.3 reverts to "improve OAR labeler accuracy."**

Three-wave context discovery (2026-05-19) evaluated the gate against live data:

- `~/.claude/cache/oar-labeled.jsonl`: **1 row total, all-time** (a `no_signal_in_window` ignored row)
- `oar-pending.jsonl`: 7 pending rows
- All-projects, 30d window, all lenses: **1 row** (UX_DESIGN, ignored)

The gate doesn't fail with a measured miss — it can't evaluate. The OAR labeler shipped in v0.5.2 has had days, not weeks, of accumulation. Continuing to spec the full workforce surface against an empty data substrate would be measurement-contaminated work (the exact failure mode the `measurement-release-discipline` memory entry calls out from v0.5.2 pre-mortem).

The redesign came from the operator: *"the system should auto-monitor for some time, and when a threshold reaches, it activates DIM with the right settings — self-learning, self-governing."*

This decouples two things v0.5.3 had previously coupled:

1. **The control logic** (gate evaluator + auto-activator) — pure code, no data dependency, ships now.
2. **The insight surfaces** (per-lens trajectory engine, anomaly flags, eventual workforce CLI) — gated on real data, light up automatically when the gate clears.

The control logic is the v0.5.3 deliverable. The insight surfaces ship as v0.5.4 / v0.5.5 / v0.6 with the gate as the inflection.

## Design: metric-gated auto-promotion from shadow to active

### Industry precedent

The pattern is **automated canary analysis** (Netflix/Spinnaker term) / **safe rollout** (Statsig term) / **guarded rollout** (LaunchDarkly term) / **dark launch with progressive promotion** (feature-flag literature). Key references: Spotify Engineering on sequential testing, AWS App Mesh + Flagger, Statsig Safe Rollout.

### What "shadow mode" means in v0.5.3 DIM

- DIM is registered (subcommand exists, lib loads, doctor check fires)
- DIM does NOT mutate operator-facing output
- DIM passively accumulates per-event labels into the existing `oar-labeled.jsonl` (zero new write path — DIM reads the existing OAR substrate)
- Every cycle a once-per-day gate check evaluates clearance; the rest of the time it's a no-op

### The gate (locked parameters)

The gate clears when **all** of the following hold simultaneously:

1. **≥3 distinct lenses** each satisfy: Wilson **99.83% LCB ≥ 5%** on `acted%` (Bonferroni-corrected from 95% over a 30-peek budget; z = 2.94 instead of 1.96)
2. **≥200 events per qualifying lens** (volume floor — prevents premature activation at low n with a chatty true rate)
3. **≥7 calendar days** of accumulation since the OAR labeler first wrote a row (calendar floor — separate from event-count floor; both must clear)
4. **No Goodhart holdout divergence detected** (see §Pre-mortem mitigations)

Power-analysis context: at true acted% = 8%, n=200 is the minimum where 99.83% Bonferroni-corrected LCB clears 5%. At true acted% = 10%, n=100 suffices but we pick 200 as the spec floor for safety. At true acted% < 7%, the gate may never clear; that is the correct behavior — if the system's advisories really are ignored that often, DIM-active outputs would be measurement-contaminated.

### State machine (3 states)

```
                            (gate clears + 7d holdout no-drift)
                            ──────────────────────────────────►
       (boot)                                                   (Goodhart drift)
shadow ─────► monitoring ─────► gated ─────► active ──────────► quarantine
                    ▲                                                  │
                    └──────────────── (force-disable) ─────────────────┘
                                              ▲
                                              │ (force-activate)
                                              └──── operator override
```

- **shadow / monitoring**: default; lib loaded, gate evaluated daily, no operator-facing output mutation. (These are aliases — `shadow` is the boot state, `monitoring` is the steady-state name; same code path.)
- **gated**: gate has cleared but a 7d holdout-validation window is still running. DIM still doesn't write to operator output.
- **active**: gate cleared + holdout validated. Future DIM-active surfaces (v0.5.4+) consume here.
- **quarantine**: post-activation, the holdout-vs-gated acted% rate diverged by >2 standard errors. Operator sees a red doctor flag; DIM falls back to shadow until manual `force-disable` then `force-activate` is re-issued.

### Operator override semantics

- `polymath dim enable` — same as `force-activate`; sets `PP_DIM_ACTIVE=1` in user.env. Idempotent.
- `polymath dim disable` — same as `force-disable`; sets `PP_DIM_ACTIVE=0`, halts monitoring. Idempotent.
- `polymath dim force-activate` — explicit verb for "I know the gate didn't clear; activate anyway." Logged in audit trail with `source: "operator_override"`.
- `polymath dim force-disable` — explicit verb for "I know the gate cleared; deactivate anyway." Same audit trail.

The convention mirrors `polymath lens-gates {enable | disable}` (kill-switch precedent) and `polymath retry-router clear-flag` (auto-state-with-override precedent).

## State files

| Path | Purpose | Schema | Retention |
|------|---------|--------|-----------|
| `$PP_CACHE_DIR/dim-state.jsonl` | Append-only state-transition log + current state | `{ts, from, to, reason, gate_snapshot:{...per-lens}, source}` | Single `.1` rotation at 10 MB (mirrors `_pp_rotate_jsonl`) |
| `$PP_CACHE_DIR/dim-gate-last-eval.jsonl` | One row per daily gate evaluation (forensic) | `{ts, lenses_qualifying:[{lens, n, acted_n, acted_pct, lcb_99_83, qualifies}], holdout_pct, gated_pct, drift_se}` | Single `.1` rotation at 10 MB |
| `$PP_CACHE_DIR/dim-last-eval-epoch.txt` | Date-based gate of "ran once today?" | Single integer epoch | None (overwritten) |

No new state files for the actual labeled data — DIM reads `oar-labeled.jsonl` (the existing OAR substrate) at evaluation time. This keeps DIM strictly a *consumer* of OAR data; if the OAR substrate ever changes shape, DIM is the only thing that needs to adapt.

## Hooking into the lifecycle

The gate evaluator runs once per calendar day. The chosen attachment point is **`hooks/inject-monitor-insight.sh`** (UserPromptSubmit hook) — it already fires on every user turn, has the right idempotency semantics, and is the lowest-friction hook to extend. A leading guard ensures the evaluator runs at most once per UTC date (epoch-floored to midnight).

The alternative was `bin/statusline.sh` (every 2s, 5-min gated) — rejected because the gate evaluation is a multi-jq pass over `oar-labeled.jsonl` (~5-50ms at expected volumes) and we don't want to pay that latency on the statusline refresh path. UserPromptSubmit already runs at non-interactive moments.

`hooks/session-end.sh` was the third candidate — rejected because it only fires at session end, which may not happen daily for long-running operator sessions.

### Concretely

```bash
# In hooks/inject-monitor-insight.sh, before the existing advisory render path:
if [ "${PP_DIM_ENABLE:-1}" = "1" ]; then
  # shellcheck disable=SC1091
  . "$PP_ROOT/lib/dim.sh" 2>/dev/null && \
    type pp_dim_evaluate_gate_daily >/dev/null 2>&1 && \
    pp_dim_evaluate_gate_daily 2>/dev/null || true
fi
```

`pp_dim_evaluate_gate_daily` is the public entry point. It:

1. Reads `$PP_CACHE_DIR/dim-last-eval-epoch.txt`; if today's UTC date matches, returns immediately.
2. Reads `$PP_CACHE_DIR/oar-labeled.jsonl` + `.1`, computes per-lens stats.
3. Applies the 4-condition gate.
4. Writes a row to `dim-gate-last-eval.jsonl` (forensic).
5. If gate clears AND current state ∈ {shadow, monitoring}, transitions to `gated` (writes to `dim-state.jsonl`).
6. If state is `gated` AND 7d holdout window has passed AND no drift, transitions to `active`.
7. If state is `active` AND drift detected, transitions to `quarantine`.
8. Updates `dim-last-eval-epoch.txt`.

Total runtime budget: <100ms at expected OAR volumes (~5k rows after a year).

## Doctor checks

### `doctor_check_dim_gate_progress` (always-yellow when not active)

```
○ DIM gate progress — monitoring (3 of 7 lenses qualify; gate clears in ~12d at current rate)
```

Returns 1 (yellow) when state ∈ {shadow, monitoring, gated}; returns 0 (green) when state = active; returns 2 (red) when state = quarantine. The detail line carries the ETA when the closest non-qualifying lens projects to clear (linear extrapolation from current acted% trajectory).

### `doctor_check_dim_data_quality` (always-green pre-activation)

Post-activation, computes the **holdout vs. gated rate divergence**: 10% of OAR rows are randomly slotted into a holdout bucket (deterministic by `hash(session_id || lens || inject_ts) mod 10 == 0`) and excluded from the gate evaluation. The holdout's acted% should statistically match the gated acted%. If `|holdout_pct - gated_pct| > 2 × SE`, that's Goodhart drift — DIM transitions to `quarantine`.

Pre-activation: green (no data to evaluate). Post-activation: green if no drift; yellow if drift in last 24h; red if drift sustained for 7d.

## Pre-mortem mitigations (per the project's 3-round review methodology)

### R1: Goodhart's Law — the metric stops measuring usefulness

When the same operator clicks generate both the gate-clearing data AND the post-gate output the operator sees, the metric optimizes for "looks like the operator acted" rather than "the operator actually found value." Statsig and the RL literature (Goodhart drift in reward modeling, arXiv 2310.09144) recommend a held-out slice.

**Mitigation:** 10% holdout slice. Slotted deterministically by hash so the same row always lands in the same bucket — important for replay/forensic auditing. Excluded from gate evaluation. Post-activation, `doctor_check_dim_data_quality` detects divergence.

### R2: Peeking / repeated-testing Type-I error inflation

Checking the gate daily over 30 days inflates Type-I from 5% to ~40% if uncorrected (Spotify Engineering on sequential testing).

**Mitigation:** Bonferroni correction. α = 0.05/30 = 0.00167 → z = 2.94 instead of 1.96. The LCB threshold becomes the **Wilson 99.83% LCB**, not the 95% LCB. The cost is requiring more data to clear the gate; the benefit is the gate-clearance event being defensibly significant.

### R3: Bootstrap bias — first week is non-representative

Early adopters and first-week behavior skew the labeled corpus. The 7-day calendar floor alone doesn't help if the first week is also the only week of data (the calendar window AND the event count both come from the same prefix of activity).

**Mitigation:** Joint requirement. The gate needs both ≥7 calendar days AND ≥200 events per lens. A single chatty session can't satisfy both — the calendar floor forces the data to span multiple days.

### R4: Operator decision fatigue (carryover from v0.5.3 vision GPT review)

The original vision worried about a "propose queue growing faster than operator processes." This is addressed by-construction in v0.5.3 because v0.5.3 has no proposals — only one binary state (`active`?). The fatigue mode reappears in v0.5.4 when proposals start landing; that risk is deferred.

### R5: Project identity leakage (carryover, partially deferred)

The vision's R2 mitigation calls for a project identity tuple (`realpath` + `.git/polymath-project-id` + machine salt). The OAR substrate already carries `project_id`, `project_root`, and `project_root_sha8` (per wave 2 OAR audit). DIM v0.5.3 reads these unchanged. The full identity-refusal logic (refuse load if mismatch) is part of v0.5.4 when state files start being per-project; v0.5.3's single shared `dim-state.jsonl` doesn't need it.

## GPT pre-implementation review addendum (2026-05-19)

Spec v1 went through two parallel GPT-5 review passes (`llm -t gaps` + `llm -t bounce`) before plan-writing. Both reviewers converged on three correctness issues. The bounce pass caught seven more defensibility issues. All findings are accepted; the spec parameters below override the v1 text where they conflict.

### P0 corrections (correctness — would have shipped a bug)

**P0.1 — CLI semantics: `enable`/`disable` must NOT alias to `force-activate`/`force-disable`.**

The v1 spec said `polymath dim enable` is "same as `force-activate`." This is wrong. The hook gates on `PP_DIM_ENABLE` (whether monitoring runs); CLI `enable`/`disable` mutated `PP_DIM_ACTIVE` (whether DIM outputs are wired). Operator running `polymath dim disable` would silently leave monitoring running.

**Locked correction:**

- `polymath dim enable` → sets `PP_DIM_ENABLE=1`. Starts monitoring. Does NOT activate.
- `polymath dim disable` → sets `PP_DIM_ENABLE=0`. Halts monitoring AND deactivates. Idempotent.
- `polymath dim force-activate` → sets `PP_DIM_ACTIVE=1` regardless of gate state. Writes audit row `source=operator_override`. Requires `PP_DIM_ENABLE=1` (refuses with rc 2 otherwise).
- `polymath dim force-disable` → sets `PP_DIM_ACTIVE=0` (operator override of cleared gate). Audit row written. Monitoring continues.

The hook always checks `PP_DIM_ENABLE` first; if 0, returns immediately. State machine transitions only happen when enable=1.

**P0.2 — Sequential-testing budget must be bounded.**

Bonferroni z=2.94 was sized for exactly 30 peeks. Daily evaluation runs indefinitely. After day 31, the FWER is no longer controlled and the gate can clear on noise.

**Locked correction:** Switch from fixed-budget Bonferroni to a **time-uniform confidence sequence** (Howard et al. 2021, "Time-uniform, nonparametric, nonasymptotic confidence sequences," Ann. Stat.). For a Bernoulli rate, the simplest CS that holds uniformly over time is the **stitched Wilson-style sequence** with variance proxy `psi = log(log(2n)) + log(2/alpha)`. The effective z-equivalent grows from ~1.96 at small n toward ~3.2 at n=10^6, never under-corrects, never burns alpha to a budget.

Implementation detail: encapsulate as `pp_dim_stats_lcb_anytime(s, n, alpha)` so the bash wrapper hides the math. The function returns the lower bound of a time-uniform 1-alpha confidence interval. Spec parameter: `alpha=0.05` (no peek budget, no expiration).

Concrete formula for `pp_dim_stats_lcb_anytime`:

```
psi = sqrt(log(log(max(2, 2n))) + log(2 / alpha))
center = (s + 0.5 * psi^2) / (n + psi^2)
margin = psi * sqrt(s * (n - s) / n + 0.25 * psi^2) / (n + psi^2)
lcb = max(0, center - margin)
```

At n=200, s=20 (10% acted, true rate ~10%), alpha=0.05: lcb ≈ 0.058. Clears 5% threshold. At true rate 7%, n=200: lcb ≈ 0.030, fails — as intended.

**Updated minimum-n table (corrected for anytime-valid CS):**

| True acted% | min n to clear LCB ≥ 5% |
|---|---|
| 8% | ~280 |
| 10% | ~150 |
| 12% | ~80 |
| 15% | ~45 |

**Locked spec floor: `n ≥ 250 gated events per lens`** (raised from 200 to absorb both holdout shrinkage AND the anytime-CS being slightly wider than fixed Bonferroni at the operating point).

**P0.3 — Per-project sharding, NOW not v0.5.4.**

v1 spec reads `oar-labeled.jsonl` without project filter and writes a single `dim-state.jsonl`. Operators with multiple projects under one `PP_CACHE_DIR` would see one project's accumulation auto-activate DIM for all projects — exactly the "project identity leakage" failure mode R2 mitigated against in the vision doc.

**Locked correction:**

- Hook + `pp_dim_evaluate_gate_daily` resolve current project's `project_root_sha8` from `lib/project-identity.sh` (existing helper from v0.5.1.1 / OAR ground work).
- OAR read filters by `.project_root_sha8 == $current_sha8` before stats.
- State files become per-project:
  - `dim-state.$sha8.jsonl`
  - `dim-gate-last-eval.$sha8.jsonl`
  - `dim-last-eval-epoch.$sha8.txt`
- A row with mismatched `project_id` (different sha8) is excluded with `silent_reason=foreign_project`. Doctor surfaces the per-project drift count.

### P1 corrections (defensibility)

**P1.4 — Calendar floor requires per-lens distinct UTC dates.**

v1's "≥7 calendar days" was global (since first OAR row written). A pathological case: 3 lenses each at n=250 all written on the same day — passes the global calendar floor but spans 1 day per lens. **Locked correction:** Each qualifying lens must show observations on **≥5 distinct UTC dates** within the window. (5, not 7, because lens activity is sparse; requiring 7 distinct dates per lens would never clear in practice.)

**P1.5 — Holdout effective-n vs raw-n.**

10% holdout means gated_n = 0.9 × raw_n. v1 floor `n ≥ 200` referenced raw_n; the power analysis assumed 100% data. **Locked correction:** Floor is `gated_n ≥ 250` (after holdout removal). Equivalent raw_n ≈ 278. Tests assert on gated_n.

**P1.6 — Quarantine auto-recovery.**

v1 required `force-disable` then `force-activate` to recover from quarantine. Bad UX. **Locked correction:** Quarantine transitions back to `monitoring` automatically when a 14-day clean window (no drift detected) passes. The auto-recovery transition is logged. Operator can still `force-activate` from quarantine if they want to override.

**P1.7 — Holdout hash needs per-install salt.**

v1's `hash(session_id || lens || inject_ts) mod 10 == 0` is deterministic but predictable. If the labeler's behavior correlates with any of those fields, holdout assignment becomes nonuniform.

**Locked correction:** Hash becomes `hash(salt || session_id || lens || inject_ts) mod 10 == 0`. Salt is per-install, written once to `$PP_HOME/dim-holdout-salt` on first DIM evaluation (mode 0600, 16 bytes from `/dev/urandom`). Doctor check validates salt presence + non-default value.

**P1.8 — Multiple-testing across lenses.**

The anytime-CS handles time-peeking but not "we tested 7 lenses; ≥3 must qualify." The "3 of 7" composite test has its own FWER. **Locked correction:** The composite gate uses a **simulation-calibrated joint threshold**: instead of "each of 3 lenses passes alpha=0.05 anytime-CS," require "each of 3 lenses passes alpha=0.05/L anytime-CS where L=7." This is a Bonferroni-across-lenses correction (within the alpha=0.05 anytime budget). The math composition is documented in `lib/dim-stats.sh:pp_dim_stats_composite_gate`.

**P1.9 — Concurrency lock at UTC midnight.**

Daily evaluation across multiple terminals can race. **Locked correction:** `pp_dim_evaluate_gate_daily` acquires `$PP_STATE_DIR/dim-eval-${sha8}.lock` via `mkdir` (same pattern as budget.sh). Lock-held: return immediately. Lock acquired: re-check "ran today?" inside the lock (double-checked locking).
