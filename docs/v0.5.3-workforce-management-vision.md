## The reframe

Three product layers, each builds on the last:

```
v0.5.1  passive advisor + cost-aware retry  ────────────  SHIPPED
v0.5.2  measurement substrate (OAR + halluc post-check)   IN PROGRESS
v0.5.3  agent workforce management + operator awareness   THIS DOC
```

The phrase "fire lens less often" is too static. The right mental model is **workforce management**: the system maintains an active roster of expert agents, and it can hire, train, promote, demote, retire, or temp-staff them based on what the work actually needs.

Slogan version: **"Pair Polymath does not just watch the code Claude writes. It learns how this project should be reviewed."**

---

## Agent lifecycle (the core schema)

Each agent in the roster has a state:

| State | Meaning | Transition triggers |
|---|---|---|
| `candidate` | Proposed by the system, not yet accepted by operator | `polymath agents accept <id>` → probation |
| `probation` | Active but on trial; metrics tracked closely | After N useful interventions → active; after M dismissed → fired |
| `active` | Standard rotation; OAR-tracked | Demoted on noise; promoted on signal |
| `promoted` | Higher injection priority / lower threshold | Earned via sustained acted-on outcomes |
| `adjusted` | Prompt rewritten (operator-confirmed) | After operator review of proposed edit |
| `demoted` | Lower priority, longer cooldown | Mixed signal — some useful, mostly noisy |
| `paused` | Temporarily not firing | Operator-set; auto-restore on event |
| `fired` | Removed from active rotation | Restorable via `polymath agents restore` |
| `temporary` | Session-scoped or phase-scoped; auto-expires | Created for specific risk pattern |

Each agent record carries:
- id, name, purpose, prompt (versioned)
- state + state-transition log
- scope: project / session / global
- expiry: timestamp or condition
- metrics: acted_on, dismissed, corrected, ignored, false_positive, interruption_value_score
- evidence basis: which observations triggered creation / promotion / firing

## The "verbs" CLI

```bash
polymath agents list [--state STATE]
polymath agents show <id>
polymath agents propose                   # system suggests; operator decides
polymath agents accept <proposal-id>      # candidate → probation
polymath agents adjust <id>               # operator-confirmed prompt edit
polymath agents promote <id>
polymath agents demote <id>
polymath agents pause <id>
polymath agents fire <id>
polymath agents restore <id>
polymath agents history <id>              # metric trajectory + state transitions
polymath agents premade                   # built-in templates
polymath agents install <premade-id>      # add a premade to roster
```

**Hard rule for v0.5.3:** every persistent state mutation goes through an explicit operator command. Auto-promotion / auto-firing / auto-prompt-rewriting is **v0.6 territory at earliest** and must be gated on OAR fidelity exceeding v0.5.3's already-elevated bar.

The system proposes; the operator decides. `polymath agents propose` is the system's way of saying "I think we need a new agent for this project" — it surfaces evidence, predicts what the agent would catch, and waits.

## Operator-aware layer (three subsystems)

The big anti-creepiness reframe: the operator-awareness layer is **not** psychological profiling. It is three local engineering-signal models, each scoped to project/session.

### 1. Flow Health Model

**Replaces "productivity score."** Reports session-state, not personal-state.

Signals (all observable from existing transcript + tool-call streams):
- Repeated failed test loops without progress
- Many tool calls without state change
- Same file edited repeatedly
- Claude claims completion without verification evidence
- User re-prompts with corrections
- User says "no", "stop", "wrong" near a Claude action
- Long session with the stated objective unresolved

Output: `flow_health: good | degraded | stuck` + reason + suggested intervention.

Intervention examples: prompt Claude to summarize state, reduce scope, run tests, identify the failing assertion. **Pair Polymath does not nag the operator** — it nudges Claude (via existing advisory injection surface).

### 2. Friction Signal Model

**Replaces "emotion profiling."** Reports interaction friction, not feelings.

Signals:
- Repeated user corrections within a window
- Rejected advisories (dismiss without ack)
- Contradiction between user request and Claude implementation
- User asks "why did you do that?" / "you missed X"
- Repeated undo/rework
- Claude continues after user wanted narrower scope

Output: `friction_level: low | medium | high` + likely cause + intervention.

Likely-cause taxonomy (closed set): `scope_drift | wrong_assumption | verification_gap | noisy_advice | unclear_goal`.

### 3. Assistance Calibration Model

**Replaces "competence inference."** Reports what kind of help is useful for this developer in this domain — never global skill.

Signals:
- User accepts direct patches vs explanations vs architecture-level review
- User dismisses basic advice
- User repeatedly requests deeper tests
- User corrects framework-specific suggestions
- User owns certain files/domains (commit history)
- User acts on certain risk classes

Output: `preferred_help_style: direct_patch | review_only | explain_tradeoffs | test_first | architecture_first` + per-domain confidence hints (e.g. "deeper assistance valued in: kubernetes, light: react").

**Strict anti-pattern list (do not build, period):**
- "User is bad at X" / "User is junior" / global competence scoring
- Working-hours analysis
- Emotional state inference (angry, anxious, frustrated)
- Personality labels (MBTI, Big Five, etc.)

The system says **"this session is stuck"** not **"this user is stuck."** The session is the unit of analysis.

## How operator awareness feeds the agent roster

The point of the three subsystems is **agent calibration**, not user feedback. They tune:

- **Interruption thresholds** per agent (when friction is high, raise the bar)
- **Agent verbosity** (when preferred_help_style=direct_patch, shorter advisories)
- **Which agents to propose** (when domain_confidence_in_X is high, retire basic-X agents)
- **Temporary agent creation** (when flow=stuck and cause=verification_gap, propose a TEST_AUDITOR temp agent for the session)

The operator never sees a personal-profile dashboard. They see: **roster decisions and their justifications.**

## What's NOT in v0.5.3

Tracked here so the v0.5.3 spec stays scoped:

- **Stop hook review** — "did Claude actually finish?" gate. Strong v0.6 candidate. Not in this layer.
- **`polymath review <target>`** — on-demand synchronous review. Right product idea, wrong phase.
- **MCP tools** (`polymath__review_diff`, `polymath__history`, etc) — depends on a stable agent surface; v0.6+.
- **Skills migration** (slash-command workflows in `.claude/skills/`) — when v0.5.3 has a clear agent abstraction worth exposing.
- **Auto-prompt-rewriting** — the temptation is huge; the risk is "system mutates its prompts based on noise." Hard rule: operator-confirmed only through v0.5.3.
- **Auto-temporary-agent-creation** — even more risky. v0.5.3 ships `propose` only. Auto-create requires OAR fidelity well above the v0.5.3 entry bar.
- **Cross-project profile sharing / cloud sync** — local-first invariant. Period.

## Open questions for v0.5.3 spec drafting

1. **Where do agents live?** `~/.claude/pair-polymath/agents/project/<project_hash>.jsonl` (the brainstorm suggested) keeps it local. Sound, but needs the project-hash function to handle worktrees + symlinks gracefully.
2. **How does an agent retire's metrics carry forward?** A fired agent might come back if its risk class becomes relevant again (project phase change). Restore should preserve history.
3. **Premade vs generated provenance** — UI clarity matters. Operator should always see "where did this agent come from."
4. **Temporary agent expiry** — by time? by phase? by N cycles? The right answer probably depends on OAR data.
5. **Backwards compat with existing 7 fixed lenses** — they need to migrate to the registry as `premade` agents with full history preserved. No silent loss of v0.5.0-v0.5.2 calibration data.
